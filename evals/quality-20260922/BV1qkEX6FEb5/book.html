1. 从无保护的机器到安全目标

(参考时间: 00:00:48–00:05:55)

早期系统为什么容易被改写

8086 实模式（早期处理器直接用段寄存器和指针计算物理地址的运行方式）把 16 位 CS 左移四位再加 IP，形成 20 位地址，因而可以寻址约 1 MB。CPU（执行程序指令的处理器）没有内存保护：一个程序可以直接修改另一个程序地址空间里的指令。int 指令通过中断向量表（把中断编号映射到处理代码地址的表）跳到固件；固件代码可以是只读的，但用户内存没有操作系统的监管、审计或隔离。

这解释了“功能能运行”与“系统安全”之间的差别：只要程序可以写别的程序，它就能植入持久行为。病毒加壳（修改可执行文件入口，先执行附加代码再跳回原入口）就是一种典型方式：游戏或编辑器表面行为不变，每次启动却先执行壳中的复制、感染代码，甚至可能破坏硬件。

网络也经历过类似阶段。讲师回忆早期 BBS（早期的文字公告与讨论系统）：登录凭据以明文传输，缺少 HTTPS（加密网页传输协议）保护，站点还可能暴露用户列表并允许脚本反复试密码。具体的校园网站故事是历史背景；真正值得保留的机制是：传输未加密、认证缺少限制时，窃听和批量尝试会把“账号秘密”变成公开数据。

CIA：安全不是只有“别人看不到”

(参考时间: 00:06:00–00:10:18)

安全的 CIA（把安全目标分为机密性、完整性、可用性的三维框架） 包含三件不同的事：

维度 要回答的问题 课上例子
机密性（Confidentiality） 不想让别人看的数据，别人能否读到？ 删除的照片、文件和手机中的指纹/人脸数据不应被随意恢复或读取。
完整性（Integrity） 不想让别人改的数据，别人能否改写？ 越权取得教务员会话后，攻击者可能看到并修改成绩；即使没有真的改自己的成绩，读权限和写权限都已暴露。
可用性（Availability） 合法用户需要时，服务还能否工作？ 把柜子锁上并扔掉钥匙没有泄露或改写物品，却让物主也无法使用。

这三个目标可能互相独立：系统把文件保护得很严，仍可能因为资源耗尽而不可用；操作系统重点提供机密性和完整性，可用性还依赖资源管理和抗拒绝服务设计。越权读取对应机密性失败，越权写入对应完整性失败，资源被恶意消耗对应可用性失败。

2. 可用性攻击与密码学的最小拼图

拒绝服务不一定靠“攻破”数据

(参考时间: 00:10:00–00:13:22)

拒绝服务（Denial of Service，让合法用户暂时无法使用服务的攻击） 直接破坏可用性；DDoS（分布式拒绝服务，由大量受控机器同时发起请求） 可以把一台服务拖垮。讲师用一个模型实验作直观例子：如果服务会把“从 1 数到一个很大的数”逐项展开，那么许多受控机器同时提交长请求，即使没有读取或修改服务内部数据，也能让输出和计算资源被耗尽。这个数字和规模是课堂设想，不是独立测量。

另一类是算法复杂性攻击（构造输入，让程序从通常的低复杂度退化为高复杂度）。哈希表平均每次查找可近似为 O(1)（输入规模增大时，单次查找平均耗时近似不变），但攻击者可以构造大量都映射到同一槽位的字符串；开放寻址或链表都会退化为近似线性处理。讲师提到的防护思路是：冲突过多时切换到最坏情况更好的树形结构，以限制攻击者把服务拖入最慢路径。

单向函数与哈希：快算正向，难求逆向

(参考时间: 00:13:25–00:15:49)

单向函数（正向计算容易、从输出反推输入很难的函数） 是密码学的基础抽象。密码学哈希（把任意输入压成固定长度、难以逆向且难以构造碰撞的摘要函数）可以很快计算大文件的 SHA-256，却难以从摘要找回原文，也难以找到两个不同输入得到同一摘要；这不是任何输入都绝对不可逆，低熵秘密仍可能被逐个枚举。它和某些语言标准库中只为快速分桶的普通 hash 不同：普通哈希可以为了取模而较可预测，密码学哈希追求输出看起来像随机值。

因此网站可以公布文件的 hash digest（文件内容经过哈希函数得到的短摘要）；下载者重新计算并比较摘要，就能发现传输或存储是否改变。这个用途是完整性校验，不等于加密：摘要公开并不会让读者获得原文件的逆向方法。

Trapdoor：同一个骨架支持加密、认证和签名

(参考时间: 00:15:52–00:19:02)

Trapdoor function（没有秘密参数时难以求逆、持有秘密参数时容易求逆的函数） 在讲师的比喻里像一把只有持有者拥有的钥匙。公开函数和算法相当于公钥（任何人都可用来执行公开操作的钥匙），秘密参数相当于私钥（只有持有者保存、用于解密或证明身份的秘密）。

  • 实现机密性：发送方用公开函数处理数据，旁观者能看到算法却无法求逆；持有私钥的一方才能解开。
  • 实现身份认证：验证方给出随机挑战；能在限定时间内用私钥求出对应答案，就证明对方掌握秘密，而不用把私钥交出来。
  • 实现数字签名：在这个课堂抽象里，把随机挑战换成文件摘要，持有私钥的一方对摘要做数字签名（用私钥对摘要作证明，让他人检查来源和完整性的结果），别人用公开信息检查签名是否匹配，从而发现文件是否被改过、是否由该密钥持有者发布。这里是共同骨架示意，不把现实中的所有签名算法等同于“用私钥解密”。

公钥本身如何可信地分发是另一个信任问题，不能因为算法公开就自动知道“这把公钥属于谁”。

区块链示例：可追加、可验证，却不负责保密

(参考时间: 00:19:14–00:24:00)

区块链（由多方共同维护、通过前缀哈希串起记录的追加式数据结构） 可以理解为一个 append-only（只允许追加、不能随意改写历史记录）的共识账本。每个新记录带着前缀哈希和签名；工作量证明（proof of work，用反复计算哈希来证明投入过算力的机制） 让追加记录变得昂贵，出现分叉时协议倾向于保留累计工作量更大的链；课堂用“更长的链”作简化说法，因而让副本逐步收敛。

这种结构的核心优点是多方共同维护带来的可用性与可验证性；它把记录公开给参与者，因此没有内置机密性。转移资产需要用私钥签名，私钥或助记词泄露就等于把转移权交给别人。课堂提到的“刻着 24 个英文单词、据说价值 1.3 亿美元”的故事被明确说成网上传闻，不能当作已核验事实。

3. 操作系统如何把访问控制放在入口处

系统调用同时规定行为和权限

(参考时间: 00:24:00–00:28:35)

现代操作系统把进程放进隔离的虚拟地址空间（程序看到的、由系统映射到真实内存的地址视图），并让程序通过系统 API 访问文件、设备等对象。计算指令可以在自己的地址空间内运行；一旦要 open、读写文件或访问设备，就必须经过操作系统提供的入口。

这个入口同时做两件事。这里的访问控制（在访问发生前判断主体能否执行某种操作的机制）正是第二件事：

  1. 行为：例如 open 成功时返回指向对象的文件描述符，read/write 执行相应操作。
  2. 访问控制：在执行行为前检查“这个进程能否以这种方式访问这个对象”。拒绝越权读保护机密性，拒绝越权写保护完整性，对资源做公平分配则能提供部分可用性。

因此访问控制不是 API 之外额外贴上的标签，而是操作系统在唯一入口处把“想做什么”和“准不准做”连在一起。进程或线程是访问主体，对象可以是文件、设备或其他内核资源。

从巨大矩阵到 UNIX 权限

(参考时间: 00:27:27–00:33:05)

访问控制矩阵（用“主体 × 对象 × 操作”的表记录允许或拒绝的模型） 的每个格子都在回答：哪个进程能对哪个对象读、写或执行？真实系统里进程、对象和操作种类太多，完整矩阵存不下；而低权限主体对绝大多数对象本来都应是拒绝，信息是稀疏的，所以系统用更小的投影来表达它。

UNIX 用整数身份和对象权限压缩这张表：

  • UID/GID（分别标识用户和用户组的整数编号） 与文件所有者、组相关联；文件权限位把读、写、执行分成“所有者/组/其他人”三组。
  • root（UNIX 中几乎不受普通权限位限制的特权用户） 的 UID 是 0。若连 root 都删不掉错误配置的文件，磁盘可能被塞满而无法恢复，反而形成拒绝服务，所以系统通常保留特权恢复路径。
  • 登录过程可以理解为：高权限程序验证密码，再把进程身份切换为登录用户；子进程继承父进程的用户身份和权限。
  • 早期密码哈希可放在 /etc/passwd，普通用户可以读取但不能改；只有特权进程能更新它。这里的重点是“验证所需信息可读”和“修改权限受限”必须分开。

setuid：解决实际需求，也扩大漏洞后果

(参考时间: 00:35:17–00:40:43)

普通用户运行 passwd 却能更新自己的密码，靠的是 setuid（执行文件时临时采用文件所有者身份的权限位）。passwd 的文件所有者通常是 root；带有 setuid 位时，它会以 root 权限运行，完成普通用户无权直接改写的操作。real UID、effective UID（当前用于权限检查的有效用户编号）、saved UID 等多种 UID 是为处理身份切换不断加上的历史机制；讲师把这类演进称为“史山”，意思是复杂系统会积累难以整体理解的补丁。

这形成清晰的风险链：程序需要特权才能工作 → setuid 给它特权 → 程序若有漏洞，攻击者就可能把普通用户的输入变成 root 权限下的行为。因此暴露在外的服务通常应以低权限用户运行，把被攻破后的影响限制在较小范围；Android 把应用分到不同用户的例子也体现了这种隔离思路。

同一矩阵的不同投影

(参考时间: 00:41:00–00:47:55)

访问控制机制只是从大矩阵中选取不同维度：

机制 把谁/什么作为主要视角 作用与代价
ACL（访问控制列表，按对象列出用户或组的细粒度权限） 文件/对象 比固定的所有者、组、其他三组权限更细，可以单独允许某个用户读而拒绝写；配置更灵活，也更复杂。
AppArmor（按程序限制其最多能看见的对象） 程序 为程序构造一个“虚拟世界”，把不该访问的路径从它的视图中抹去；程序被攻破时，能看到的范围仍受限。
seccomp（在进程边界过滤系统调用） 进程/API 在可调用的入口处加门，只放行需要的调用；规则越细，维护和兼容成本越高。
eBPF/LSM（把受限检查程序挂到内核安全钩子上的机制） 每次访问 检查代码返回允许或拒绝，可以更贴近每次 API 访问；检查越强，运行时开销和策略复杂度越高。

seccomp 在进程边界过滤系统调用；eBPF/LSM 把受限检查代码挂到内核钩子，让每次检查返回允许或拒绝。讲师用“为每次访问运行图灵完备检查，甚至调用大语言模型”说明理论上的细粒度上限；这只是能力边界的设想。工程实现必须在安全、性能和可维护性之间取舍。

4. 访问控制挡不住程序自己的异常路径

模糊测试把“没想到的输入”变成证据

(参考时间: 00:47:56–00:51:08)

即使进程权限设置正确，程序内部的 bug 也可能让它走到非预期路径。模糊测试（自动生成大量异常、随机或边界输入来寻找未预料执行路径的测试方法）把“用户会怎样使用程序”的未知变成可重复的失败证据。整数下溢等异常状态可能导致余额从 0 变成极大值；这说明输入验证和状态约束仍是系统安全的一部分。

讲师还判断：随着大语言模型参与找漏洞，复杂系统中的漏洞发现成本可能下降，攻击者手中的 zero-day（尚未公开、通常还没有补丁的漏洞）数量可能增加。这里是讲师的趋势判断，不是已盘点的数量。

缓冲区溢出如何变成控制流劫持

(参考时间: 00:51:00–00:56:30)

经典栈溢出（固定大小的栈内存区域被越界写入并破坏相邻数据）可以按一条因果链理解：

  1. 函数在栈上分配固定大小的 char buffer，却用无界输入读取；
  2. 过长输入越过数组边界，覆盖栈上的返回地址；
  3. 函数执行 return 时，CPU 把被覆盖的地址当成下一跳；
  4. 若攻击者能构造合法地址和参数，控制流就可能跳到危险函数；若该程序带 setuid 并以 root 运行，普通用户输入就可能升级成 root shell。

早期攻击还会把 shellcode（注入内存、用于执行攻击者指令的一小段机器码）放进栈里，再把返回地址指向它。这里的关键不是某个具体 payload，而是：内存写越界改变了控制流；特权身份又放大了后果。

防御与绕过形成攻防循环

(参考时间: 00:54:10–01:02:08)

防御 主要思路
NX/DEP（把数据页标成不可执行） 栈上即使出现注入代码，CPU 也不能把它当指令运行。
ASLR（每次运行随机化地址空间位置） 攻击者难以预先知道栈和代码地址，合法跳转更难构造。
Stack canary（金丝雀：返回前检查的随机哨兵值） 溢出覆盖返回地址时通常也会覆盖哨兵；返回前发现值变了就中止。
CFI（控制流完整性：只允许预先认可的间接跳转目标） 让返回或间接分支只能落到合法入口，减少任意 gadget 串联。

NX 促成了 ROP（返回导向编程，利用已有代码片段而不在栈上执行新代码）：攻击者把多个地址放进栈中，每个地址指向以 ret 结尾的 gadget（可拼接的短代码片段），如 pop rdi; ret，让已有指令按攻击者安排的顺序运行。CFI 等机制再限制这些跳转。防御不是一次性解决方案，而是随着攻击路径改变而继续加固；若能接受运行时开销，动态检查和沙箱可以进一步缩小攻击面。

5. 侧信道：程序“没返回数据”也可能泄密

时间把密码比较变成可观测信号

(参考时间: 01:02:25–01:06:49)

侧信道（不经正常数据返回路径，而从时间、缓存、功耗或电磁等副作用推断秘密的通道） 不要求程序有明显逻辑漏洞。讲师的密码核对例子在错误时统一 sleep 3 秒，看似能阻止爆破；攻击者仍可操纵内存布局：把待猜字节放在页边界，并制造内存压力让该页被换出。

  • 猜中第一字节时，比较会继续访问下一页，触发缺页并变慢；
  • 猜错时，比较立即返回，访问较快；
  • 重复测量时间，就能逐字节判断猜测，再把边界移动到下一字节。

所以每次逻辑比较都遵循代码，并不意味着秘密不会泄露；时间差本身就是输出。这也是为什么防爆破的等待不能替代对访问模式和时间泄漏的审查。

Meltdown：回滚指令，缓存痕迹仍在

(参考时间: 01:06:49–01:12:08)

Meltdown（利用投机执行与缓存痕迹越过内核/用户边界推断数据的漏洞）利用了投机执行（CPU 为隐藏延迟而预先执行尚未确认路径的指令）与缓存的组合缺陷。攻击者先安排一次本应触发权限异常的读取；在异常真正提交前，CPU 可能暂时把内核字节读入寄存器，再用该字节选择一个数组位置，令对应缓存行变热。异常发生后，指令结果会被丢弃，但缓存状态留下了痕迹。

另一个线程逐个测量候选地址的访问时间：缓存命中更快，因而可以推断那个内核字节。讲师强调，这是 CPU 设计、预测、权限检查和缓存共同作用的结果，不是普通应用 API 主动返回了内核数据。此后内核减少或避免把内核与用户进程映射在同一地址视图中，降低同类读取的机会；这是一种针对该类机制的隔离修补，不代表所有旁路漏洞消失。

物理层也会留下旁路

(参考时间: 01:12:08–01:14:53)

讲师还举了三个方向：天线可从显示器的电磁辐射还原屏幕，近距离传感器可能从 CPU 电磁信号推断私钥，断电后用低温维持 DRAM 数据的冷启动攻击（利用断电后短时间残留的内存内容恢复秘密）。它们共同说明安全边界不只在软件 API：程序 bug、微架构副作用和物理信号都可能成为观测通道。

6. AI 时代的攻击面：输入、工具和依赖

Prompt injection 不是“模型突然变坏”

(参考时间: 01:14:56–01:17:10)

Prompt injection（把恶意指令藏进输入或上下文，诱导模型偏离原任务的攻击） 和 jailbreak（通过构造对话绕过模型安全限制的尝试） 利用的是模型会把上下文当作行为依据。讲师回忆早期模型可被“奶奶睡前故事”这类包装诱导，也可伪造一段 chat history（对话历史），让模型把攻击者预填的内容误当成自己已经说过的话。随着训练和后训练改进，这些方法可能变难，但讲师明确认为很长上下文、权重修改等路径仍可能破坏安全策略；这些是课堂判断，不是对当前模型的保证。

Agent 权限越大，注入后的后果越大

(参考时间: 01:17:10–01:19:04)

当 Agent（能根据模型输出调用工具、文件或网络服务的自动化程序）会读网页、写文件或调用 API 时，注入可以被拆成多次看似无害的片段：每次只让 Agent 写入一点内容，等文件被读取后再拼成恶意指令。恶意网页也可能把提示藏进学习资料；小模型反复读入、未经清洗地粘进上下文后，可能把 API key（调用服务的秘密凭据）外传。

沙箱（把程序限制在隔离环境中的执行边界） 与最小权限（只授予完成任务所需的权限）是主要缓解方向：只给 Agent 完成任务所需的文件、网络和工具权限，即使提示注入成功，能造成的损害也较小。但存在明确的可用性张力：权限越少，任务越常因缺权限中断；权限全开，工具越好用，注入后的爆炸半径越大。讲师的结论是访问控制在 Agent 时代仍然是核心，而不存在“绝对防御”。

供应链：一次安装可能把下游全部带入风险

(参考时间: 01:19:04–01:24:12)

供应链攻击（污染被许多项目依赖的上游组件，让下游在更新时一起中招） 的典型链条是：

  1. 攻击者先取得维护者的仓库密钥，或长期建立信任；
  2. 发布名称看似正常的恶意包，把行为藏进合法功能；
  3. 包管理器的 install hook（安装时自动运行的脚本）在安装或更新时执行；
  4. 脚本扫描当前用户可见的配置文件、环境变量和 API key，并把秘密发送出去；
  5. 一旦进入依赖关系和 CI/CD（持续集成/持续交付的自动构建与发布流程），下游用户更新就会扩大影响。

这里的风险不只来自“坏代码”，还来自安装流程默认允许执行脚本、用户目录本身拥有高价值凭据等组合条件。防范方向是依赖审查、最小权限、可复现构建、密钥不入仓库，以及对生产行为做严格测试；它们降低风险，却不能把复杂供应链变成绝对安全。

讲师用 xz-utils 后门作更长期的例子：攻击者据称花数年建立贡献者信任，在构建系统中混入难读的恶意修改，并让检查脚本无法编译，从而避开一部分自动 fuzzing；下游已经受污染时，一个性能异常反而暴露了问题。名称和归因按字幕保留为课堂案例，细节未作外部核验。这个例子留下的工程教训是：构建链、依赖更新和生产性能都需要独立观察，偶然的性能回归也可能是安全线索。

7. 复习主线

(参考时间: 01:24:07)

  • 先问安全目标：数据是否应被看、被改、被阻断使用（CIA）。
  • 再找边界：现代系统把对象访问收束到 API，并用矩阵的不同投影表达主体、对象和操作之间的允许关系。
  • 再查异常：特权程序、无界输入和控制流跳转会把一个局部 bug 放大成权限提升。
  • 最后查副作用：时间、缓存、电磁和残留内存都可能泄露没有直接返回的数据；AI Agent 的输入、工具和依赖也应按同一套最小权限原则审视。
